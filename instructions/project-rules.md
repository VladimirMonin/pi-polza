# Постоянные правила проекта

Жёсткие инварианты `pi-polza`. Нарушение любого из них — **баг, даже если тесты зелёные**.

Правила постоянные: они не зависят от текущей задачи и не отменяются новым ТЗ.
Главный принцип: **сначала доказательство фактического поведения → потом реализация.**

## 1. Честность данных

- Неизвестное значение — **`unknown`**, никогда не `0` и не правдоподобная догадка.
  Пустое место не заполняется «разумным предположением».
- Capabilities — **tri-state**: подтверждено / опровергнуто / неизвестно.
  Отсутствие подтверждения **≠** `false`.
- `reasoning_tokens === 0` **≠** reasoning выключен. `offVerified` выставляется только при прямом
  доказательстве; подтверждение уровней — только при воспроизводимых доказательствах на нескольких
  запросах.
- Сырые транспортируемые значения не называть «mapped».
- Приоритет метаданных: **override → Polza → OpenRouter → unknown**.
  OpenRouter — только обогащение, сопоставление строго по точному id модели, без догадок.
- Никогда не подменять `unknown` / `not verified` догадками.

## 2. Деньги и учёт

- Фактическая стоимость — только **`usage.cost_rub`** от Polza (авторитетный источник).
- **Никогда** не писать RUB в долларовое поле `cost` в Pi — там намеренный `0`.
- Не оценивать расходы сессии по ценам за токены; цены каталога — только ориентир.
- Никакой конвертации валют (FX).

## 3. Безопасность

- `POLZA_API_KEY` **никогда** не попадает в stdout/stderr, трейсы, журналы сессий или ошибки.
- Заголовок `Authorization` удаляется перед любым HTTP-логированием.
- `.env` в `.gitignore`; секреты не коммитить. Перед релизом проверяются точный public candidate, история и состав artifact. Legacy `npm run audit:secrets` содержит привязанные к машине workspace roots и dotenv-поведение: без отдельно согласованного scope его не запускать. Использовать bounded public scan без чтения домашних credentials/runtime; значения находок не печатать, точечные synthetic/provenance совпадения классифицировать, не отключать detection.
- Установленный пакет **не читает** `.env` из исходного checkout — только `<cwd>/.env` или
  `PI_POLZA_ENV_FILE`.
- Плагин не хранит собственных учётных данных — только нативное хранилище Pi.

## 4. Нативные механизмы Pi

- Не изобретать хранение секретов — использовать нативный auth / credential store Pi.
- Только семантические цвета темы (`ctx.ui.theme.fg(...)`), никаких hardcoded ANSI/RGB.
- Не добавлять собственные обёртки транспорта там, где есть нативные механизмы Pi.

## 5. Процесс

- Работать по todo-листу и **отмечать пункты сразу** по завершении.
- Мелкие логические коммиты; не выходить за рамки задачи; без scope creep.
- Не переписывать историю: никаких `amend` / `rebase` / `push --force` на запушенном.
- Push, tag и release выполняются в действующем прямом scope владельца; уже выданное разрешение не нужно получать повторно. Общим index управляет назначенный координатор. Без `npm publish`.
- Для известного дефекта: ожидаемое/наблюдаемое → воспроизведение → минимальная правка → адресная проверка настоящего пути → завершение. Начинай с существующих affected tests; полный suite — на границе выпуска или при общем impact. Применимые неизменённые результаты переиспользуются со своими версиями и областью, не обнуляются новой датой.
- Отдельный живой эксперимент нужен при существенной неопределённости **внешнего контракта**. Заранее задай вопрос, конечный сценарий и бюджет в разрешённом scope. Настоящий Pi lifecycle с synthetic HTTP не выдаётся за live service. Заметка в `notes/` нужна для самостоятельного долговечного знания, не каждой опечатки.
- Установка опубликованного пакета не наследует процедуру разработки нового выпуска. Local checkout, Git-install и опубликованный artifact — разные источники; metadata версии не доказывает доставку.
- Для актуальной внешней документации: Context7 `resolve-library-id` → нужная версия → `query-docs` → конкретное решение. При отказе — официальный первичный источник с версией и способом получения. Для локальной опечатки сеть не нужна.

Детали коммитов, тегов и релизов: [commit-and-release-guide.md](commit-and-release-guide.md)

## 6. Что НЕ является постоянным правилом

Область работ задаётся текущим ТЗ. Запреты отдельных итераций (медиа-генерация, TTS/STT,
embeddings, routing и профили, dashboard, FX, сабагенты и т.п.) — это ограничения конкретной задачи,
а **не** инварианты проекта. Их нельзя закреплять здесь навсегда: следующая итерация иначе упрётся
в собственные инструкции.

## 7. Диагностика и хранение

Используй существующие уведомления Pi, footer/panels, stderr opt-in и session accounting, не новый постоянный JSONL-логгер. Полезны stage/version, auth source/state **без credential**, catalog outcome/count, ожидаемые/фактические provider/model и причина отказа. Не весь объект, каждый токен или повторяющееся событие.

Не добавляй по умолчанию запись ключей, HTTP Authorization, личных запросов/ответов или памяти. Обычная история Pi и явный Trace — отдельные sensitive stores, не разрешение дублировать их в diagnostics. Trace принимающей сборки остаётся default-off.

| Канал/данные | Фактическое хранение и очистка |
|---|---|
| Уведомления, footer/panels, stderr | Provider не создаёт отдельного файлового журнала. Размер/срок перенаправленного shell output ограничивает владелец запуска; автоматическая ротация не заявляется |
| `POLZA_DEBUG_PAYLOAD=1` | Ограниченный stderr opt-in для reasoning-полей, не полная безопасная выгрузка body. Не включать постоянно и не расширять на messages/headers/tool payload |
| OpenRouter cache | Один заменяемый `openrouter.json` в cwd потребителя; TTL свежести **24 часа**, не срок хранения. Stale/corrupt файл автоматически по возрасту не удаляется; адресная очистка после остановки его потребителей |
| Accounting в session entries Pi | Provider не задаёт отдельный TTL/size cap/автоудаление. Не обрезать историю ради диагностики: это меняет сохранённый учёт |
| Trace принимающей сборки | Явный opt-in; отсутствие retention/rotation у `pi-trace-extension` — отдельный конкретный остаток компонента, не повод переписывать Polza logging |

Если меняется фильтр, проверь настоящий записанный выход на synthetic данных: нужные числа/причины присутствуют **и** secret/content sentinels отсутствуют. Пустой файл или выключенный logger не доказывает фильтрацию. Raw evidence/backups остаются приватными, публикация — только санитизированного итога.
