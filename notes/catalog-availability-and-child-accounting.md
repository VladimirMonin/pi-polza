# Доступность каталога и учёт фоновых подагентов

Запись о срезе `Unreleased` (после v0.2.2, Pi 1.4.0, Node 25.8.1). Ничего не публиковалось,
тег не двигался. Платных запросов к моделям не было.

## Что было не так (наблюдения пользователя)

1. В списке провайдера `polza` отсутствовали популярные модели — в частности
   `anthropic/claude-sonnet-5.5` и `anthropic/claude-opus-5.5`, хотя они есть в каталоге Polza.
2. Расходы фоновых подагентов на Polza не попадали в учёт сессии.
3. Для `moonshotai/kimi-k3.1-pro` «не видно расходов».

## Доказательства

- Живой каталог Polza: 405 записей, 300 `type=chat`, 300 с `/api/v1/chat/completions`.
  274 записи имеют и `context_length`, и `max_completion_tokens`; у 26 чат-моделей
  `top_provider.max_completion_tokens === null` (верхнеуровневое поле — точное зеркало,
  0 расхождений по всем 405 записям).
- `metadata/eligibility.ts` отбрасывал модель при неизвестном пределе ответа и при неизвестных
  modalities. Итог: 300 − 26 = 274. Совпадало с `~/.pi/agent/models-store.json` (274).
- Справочник OpenRouter в рантайме не участвовал: путь кэша выводился из `process.cwd()`,
  сессия шла из `C:\Users\User`, кэша там нет → `openRouterSource = "none"`. Локальная копия
  в репозитории была от 2026-09-21 и моделей 5.5 не содержала.
- `/polza-refresh` при этом сообщал успех: `getLastBuildInfo` собирался, но ни одной командой
  не вызывался, поэтому деградация была невидима.
- Мост к pi-subagents не активировался никогда: `advertisedCompletionEvent` читал
  `reply.events`, а установленный pi-subagents 0.79.1 отвечает конвертом
  `{version, requestId, method, success, data:{events}}`. Проверено на настоящем RPC без моделей:
  `replyKeys=[version,requestId,method,success,data]`, `active=false`, `forwardedChildren=0`.
- Следствие: во всех просмотренных журналах сессий записей `origin:"background-subagent"` — 0,
  при этом дочерние `run-0/session.jsonl` с провайдером `polza` содержат 4517 записей
  о расходе (~1500 ₽). Тест `tests/subagents-bridge.test.ts` закреплял неверный контракт.
- `stream-accounting.ts` при неуспешном терминале заменял уже полученный `cost_rub` на `null`:
  оплаченный, но оборванный ответ терял измеренную стоимость.
- `presentation.ts` считал полноту только по отсутствию `costRub=null`, поэтому панель писала
  `Completeness: complete` при полностью отсутствующем фоновом учёте.

## Решение

- Неизвестное — не отрицание. Отказ остаётся только для доказанно непригодных моделей
  (не чат, нет chat-completions, известны только не-текстовые данные, нет размера контекста).
- Неизвестный предел ответа ограничивается размером контекста: это физический потолок, а не
  выдуманная константа; Pi дополнительно урезает запрос по свободному месту. Неизвестные
  modalities на чат-модели трактуются как текст (единственный входной тип, который Pi может туда
  отправить).
- Копия справочника читается как свежайшая из проект-копии и общей, пишется в общую — одна
  ступень вместо копии на каждую папку запуска.
- Мост читает `data.events`, при `success: false` не активируется; плоское тело ответа остаётся
  совместимым. `bridge.ready` отличает «pi-subagents нет» от «есть, но не договорились».
- Панель показывает состояние импорта и не заявляет полноту без него.
- Измеренная цена сохраняется при обрыве; в аномалию добавлена причина терминала.

## Проверки

- `npm test` — 206 PASS, 8 FAIL. Все восемь — `tests/startup-native.test.ts`, падают из-за
  отсутствия установленного `@earendil-works/pi-coding-agent` в checkout (предсуществующее
  внешнее условие, к этому срезу отношения не имеет).
- Офлайн-пересчёт реального снимка каталога настоящими `resolveModels` + `toProviderModelConfigs`
  с пустой картой OpenRouter: было 274, стало **298**; оба Claude 5.5 присутствуют, 24 модели
  получили предел, ограниченный контекстом.
- Не проверено: живой ответ каталога Polza, реальный `/polza-refresh` с записью кэша, полный
  фоновый цикл «ребёнок → завершение → запись в родителя», фактическая видимость строки футера
  в TUI при конкретной ширине окна. Ничего из этого не выдаётся за проверенное.
